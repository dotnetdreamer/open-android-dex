# Remote desktop: the phone's own screen, from a computer

LinuxOnDroid can show this phone's own Android screen on a computer and take the computer's mouse and keyboard back, from the same room or from anywhere. It is what people use TeamViewer QuickSupport for, without an account, without a server anybody pays for, and without an add-on from the phone's maker.

What a person does:

1. **Phone:** LinuxOnDroid → Settings → *Remote desktop* → turn it on. Android asks once whether to share the screen. *Turn on control* explains what the accessibility service does, then opens Android's page for it
2. **Phone, once per computer:** *Add a computer* shows an eight-character code (the Remote access page, the same pairing as Linux's)
3. **Computer:** Open Android DeX → the *Linux* tab → type the code. From then on that phone has a *Phone screen* button, which opens the phone's screen in a window of its own
4. **Or a browser, nothing installed, on the same Wi-Fi:** the card shows an address and a code; the page there (`phone.html`, from the same door as LinuxOnDroid's *Open in a browser*) is the phone's screen
5. **Or a browser from anywhere:** *From anywhere, in a browser* on the card asks Cloudflare for a web address (a quick tunnel, free, no account) that leads to the same door; the same code opens it. A second way, not published yet: a static page (`openandroiddex-remote/web`) that joins the phone's own tunnel as WebAssembly, pairs with the eight-character code like a computer, and sends the picture straight between browser and phone by WebRTC where the networks allow

This record exists for the same reason `web-viewer.md` and `remote-access.md` do: several decisions below look arbitrary until you know what Android refuses, and they were checked on a Galaxy S25 Ultra on Android 17.

## No server to pay for

The picture goes through the tunnel Remote access already has (`remote-access.md`, "Why iroh"): QUIC between the computer and the phone, end to end encrypted, dialled by key. Hole punching finds a direct path in roughly nine cases in ten, and then nothing but the two ends carries the video. The rest goes through n0's public relays, which cost nothing and need no account.

Said plainly, because it is the one dependency: n0 describes the public relays as being for development and hobby use, rate-limited and without an SLA, and sells relays for production (from $19 a month in November 2026). The relay is open source, and `dexremote serve --relay <url>` points a phone at anyone's own. A remote desktop that ends up on a relay is usable, not fast; the window's title says when it is.

The two ways for a browser from anywhere lean on free services too, each with its own limit:

- **Cloudflare quick tunnel.** Cloudflare documents quick tunnels as being for testing and development, with no uptime guarantee, and the address is a random name that changes every time cloudflared starts (a restart, an update, the switch). A named tunnel would keep one address, and needs a domain and a Cloudflare account. cloudflared is built for `GOOS=android` with the NDK (its Linux build's DNS needs `/etc/resolv.conf`, which Android has not) and ships as `libcloudflared.so`, 29 to 31 MB per ABI, which is most of what this feature adds to the APK
- **The page from anywhere.** A browser has no UDP of its own, so iroh in a browser only ever reaches the phone through n0's relay. The page therefore asks for WebRTC over that relayed link: the browser's offer, the daemon's answer (`rtc.rs`, str0m), and ICE tries every pair of the two ends' addresses, host and server reflexive. Server reflexive means asked of a public STUN server (Google's and Cloudflare's, free); both ends' public addresses are then known to that server, as in any WebRTC call. There is no TURN relay, which would be a server to pay for: where both ends sit behind strict NATs (some mobile carriers, some offices) no direct pair exists, and the page keeps the n0 relay, as its status line says ("through a relay" instead of "direct"). WebRTC costs the phone's daemon about 3 MB per ABI (str0m, its SCTP, and AWS-LC, which its DTLS uses for certificates; the NDK's clang builds it without CMake)

## Two pictures, because Android allows two

**Screen sharing** (`PhoneScreen`) is the screen as it is drawn, sixty times a second, on the phone's hardware encoder. Android asks the user every session, and from Android 15 QPR1 it ends a projection the moment the lock screen shows and refuses to start one under it (AOSP's MediaProjectionStopController; flags always on in 16 and 17). From Android 16 an injected touch on the dialog's Start button is dropped for any accessibility service that is not an accessibility tool. So nothing an app does can bring screen sharing back with nobody at the phone.

**The slow view** (`PhoneShots`) is what still works then: the control service's own screenshots, at most one every 333 ms, encoded on the same hardware into the same stream. The lock screen is in them. A computer that opens a locked phone wakes it, sees its lock screen, and someone who knows the PIN can unlock it from the computer as they would by hand. Windows an app marks secure are black, as in screen sharing.

The stream takes whichever is there, best first, and switches as they come and go. The video message says which (`"source":"screen"` or `"shots"`), and the window says *Full speed* or *Slow view*, with a button that asks the phone for screen sharing.

### Where the work happens

On the phone's graphics and video hardware: Android draws the screen into a GPU buffer (the virtual display's SurfaceTexture), one GL draw makes the picture its size (the quality and Picture size) on the GPU, and the phone's hardware H.264 encoder compresses it (the video message says which: `c2.qti.avc.encoder` on the Galaxy S25 Ultra, `OMX.qcom.video.encoder.avc` on a Redmi Note 7, both `"hw":true`). No pixel goes through the CPU on that path; the CPU moves only the compressed bytes to the network. The slow view's screenshots go to the same hardware encoder. On the computer, the browser or the app decodes with WebCodecs, in hardware where it has it. On a Redmi Note 7 (Snapdragon 660), one sample from its viewer (2026-11-21): 19 frames a second at 886x1920 (Medium on its 1080x2340 screen), and 31.6 ms a frame from the GL draw that makes the frame to its encoded bytes (the stats message's `encodeMs`: the draw, the encoder's queue and the encoding). Whether the encoder alone holds it at 19, and how much a smaller picture would help on that phone, was not measured.

### Why the encoder is fed through a texture

Screen recorders give the virtual display the encoder's surface directly. Then every frame the screen makes is encoded, and a link that cannot carry them can only queue them (lag) or drop encoded frames (a broken picture until the next key frame). Here the display draws into a SurfaceTexture, every buffer is taken off it at once, and one GL draw sends the newest picture on when the session has room: the rule LinuxStream keeps by asking Xvnc for an update only when the window allows. The draw costs about a millisecond. One virtual display per projection (Android 14 allows one), resized when the screen turns or the quality changes, and given no surface while nobody watches.

## Unattended access

`adb shell cmd appops set <package> PROJECT_MEDIA allow`, once, from a computer: Android then asks nobody, and lets the projection go on when the phone locks and start while it is locked. On the S25 the system logs it in those words: `MediaProjectionStopController: Continuing MediaProjection for package with OP_PROJECT_MEDIA AppOp`. With it, a computer that opens the phone gets full speed at once, locked or not, and with *Ask to share the screen after a restart* on, sharing starts after a restart with nobody there (after the first unlock, when Android starts apps at all).

The app cannot give itself the app-op, and says when it has it (the card's green line). Uninstalling the app takes it away; `PROJECT_MEDIA default` does too. The notification and Android's own sharing indicator still show while the screen is shared.

TeamViewer and AnyDesk document no unattended Android access without the phone maker's add-on. This needs one command, once.

**Shared only while a computer watches.** Until 2026-11-22 the share, once given, was held for as long as Remote desktop was on, ready for the next computer. Android 15 and later hide the details of the phone's own notifications while any screen is shared (screen share protections), and the user found on the S25 (Android 17) that they could neither read nor swipe their notifications while Remote desktop was on, and could again once it was off. With unattended access the share now ends 15 s after the last computer leaves (`PhoneRemoteService.idleCheck`, also after a share made with nobody watching) and comes back by itself for the next one, in about 100 ms. The 15 s keep it through a page reload. Without unattended access the share was still held, because only someone at the phone could give the next one, so a phone set up the normal way (the user's Play install, the same evening) still hid its notifications all day. Since then every phone stops sharing 15 s after the last computer leaves (`PhoneRemote.stopsWhenIdle`), unless *Keep full speed ready* is on (`PhoneRemote.keepsReady`, the user's choice of three, off by default): a phone without unattended access then asks for no share when Remote desktop is turned on or after a restart (*Ask to share the screen after a restart* shows only with *Keep full speed ready*), and the next computer's arrival asks someone at the phone, with the slow view until someone allows it. The card says so in blue rather than amber, as nothing is missing. *Keep full speed ready* keeps today's held share for people who need full speed with nobody at the phone, and its words say what it costs. Unit tests: `PhoneRemoteSettingsTest` (the switch's default, what turning Remote desktop on asks, the restart question, `stopsWhenIdle` and `asksAfterRestart`). **Checked** on the S25 (Android 17), 2026-11-22 20:04, a debuggable 0.3.42 with control on (scratchpad `share-idle-attended.mjs`; each share started with unattended access and the app-op set back to default while the computer watched, as no consent can be tapped there): without *Keep full speed ready* the share ended 15.7 s after the computer left; with it, still held 30 s after; SystemUI's notification filter (`mHideSensitive` in its dump) read true while the screen was shared and false once it was not. The user's Play install (0.3.40) had held its share with no computer connected (19:05). After a share ended by itself, the next computer, with nobody at the phone, got the full picture ("screen", not the slow view) 3.3 s after opening (`reconnect-check.mjs`, unattended access). **Checked** on the S25 (scratchpad `share-idle-check.mjs`, a client of its own with `wake:false`): before, `dumpsys media_projection` showed the app's projection with no computer connected (17:39); after, shared while the computer had the phone, still shared 5 s after it left, ended 16.3 s after it left.

## Control is accessibility

`INJECT_EVENTS` is the system's. What an app can do is `dispatchGesture`, which every app sees as a real touch, the global actions (Back, Home, Recents, notifications, quick settings, power menu, lock, screenshot) and, from Android 13, an input method of the service's own (`flagInputMethodEditor`) that commits text at the cursor and sends key events into the focused field whatever keyboard the phone uses. Before 13, typing sets the focused field's text through its node.

- The left button is a finger, held as long as the button is. A drag is a queue of continued strokes, newest position first, as `WebInput` does. Each leg lasts as long as the computer took between the two positions (by when they arrived), and a release where the finger already is lifts at once
  - Until 2026-11-21 every click was a long press and every drag a run of new touches: a press recorded its button and then cleared it again (`endDrag`), so the release was ignored, and a still finger was drawn one pixel long, so the system refused the next leg as a "points mismatch". The person testing from a browser found it on the first try. The test pad now reports how long the phone held each touch, and the checks look at the release as well as the press: 20 clicks of 100 ms through Cloudflare were held 98 ms (median) on the phone, none a long press; before, none of 20 ended with a finger up at all
  - Until 2026-11-22 a move to the pixel where the finger already was (a pen's pressure changing, a second button pressed, a jitter smaller than a pixel) left the finger down after the release. A continued leg that does not move makes no events, and Android answers it as cancelled while the finger stays down (`MotionEventInjector`: no events, `notifyService(false)`); the cancel dropped the drag's stroke, so the release had nothing to lift. Such a move now gets no leg. On the Redmi Note 7, raw pointer messages on the page's socket, the test pad's log (`wheel-scroll.mjs --only drag`): before, a press, a move to the same pixel and the release gave a press and no lift (the next click's finger cancelled the touch), and so did a 300 px drag that ended with a move to the same pixel; after, a lift 164 ms and 708 ms after the press, while a 1-pixel move and a plain drag behaved as before. Whether this was the press-and-hold the person testing saw fail on that phone is not known
- A held button is a held finger, so a long press is the phone's own: on the Galaxy S25 Ultra (Android 17), six one-second holds reached the test pad as touches of 959 to 1053 ms (2026-11-21). Whether Android cancelled any of them was not recorded: the pad says so for each touch (`cancelled`), but until 2026-11-22 the harness kept only each touch's time, and a cancelled touch has a time too. It now keeps the whole touch (time, moves, cancelled). Run again on 2026-11-22 (the S25, the door's page over Wi-Fi): six one-second holds arrived as touches of 810 to 1134 ms (median 1025), all six long presses, none cancelled, no moves; ten 100 ms clicks as 82 to 174 ms, none past 500 ms, none cancelled, no moves. The person testing saw press-and-hold fail on a Redmi Note 7 (MIUI 12.5, Android 10); not reproduced or explained yet: control was off there when it could be looked at, and the phone has no adb. Reports elsewhere describe continued strokes that Android accepts and then cancels on some phones, which would do this
- Right button Back, middle button Home, as in scrcpy
- The wheel and a touchpad scroll the phone's page as far as a page on the computer would, on the computer's screen: the page or the window sends each wheel event's distance in the phone's pixels (`0x13`, see "The wire"), a touchpad's momentum included, and a finger of its own (`PhoneInput.scroll`) stays down while they come. It goes down where the mouse is, moves just past the touch slop in a leg of its own, then covers the distance in continued strokes of 8 ms, eased over a few frames; when nothing more comes it holds still for 50 ms, then moves one last pixel and lifts, so a velocity tracker sees no speed and the page does not fling on. Shift turns the wheel sideways; Ctrl and the wheel (a pinch) scrolls nothing. A click takes the finger from a scroll at once
  - Until 2026-11-22 each notch was a 90 ms swipe of its own, and on a Redmi Note 7 (Android 10) the wheel scrolled nothing. Android 10 samples an accessibility gesture every 100 ms, so the swipe reached the app as a press, one move and the lift, and a list whose items take touches (Settings, the test pad's page) takes the move that passes its touch slop as the slop: nothing was left to scroll (0 px in Settings for every input, 0 on the test pad's page; sideways, where the view itself takes the touch and only subtracts the slop, 154 px a swipe). Notches closer than about 115 ms cancelled each other before their one move (14 of 15 in a fast spin), and a click within about 100 ms of a notch stayed down: the swipe's cancel, caused by the click's own finger, cleared the click's state, so its release was dropped
  - The first leg after the slop lasts 24 ms: an app gets the moves of one frame as one event, and a list takes the whole event that passes its slop as the slop. With 8 ms that leg often shared the slop's frame: one notch scrolled Settings 160 of 326 px, a fast spin 66% of its distance on the test pad
  - Measured on the Redmi Note 7 through the door's page in Edge, 2026-11-22 (`test/phone-remote/wheel-scroll.mjs`; the test pad's scrolling page, which a build shows when `files/phone-remote/testpad` says `scroll`; the picture drawn 717 CSS px tall, so one CSS px was 3.26 of the phone's pixels): one notch (100 px) 323 of 326 px; three notches 120 ms apart 955 of 979; a fast spin of 15 notches 18 ms apart 4842 of 4896, done 590 ms after the finger first went down (the spin took 258 ms, and five fingers went down one after another, each with half a screen of room); a touchpad swipe (51 events at 60 a second, momentum included) 1070 of 1073; sideways 1073 of 1073; Shift and three notches 982 of 979; three touchpad swipes in a row 3180 of 3218. Nothing moved after any lift. In Settings: a notch 318 of 326, three notches 959 of 979, three quick notches 977 of 979, a touchpad swipe 1066 of 1073. Clicks right after a notch (30, 80 and 200 ms), during a touchpad's momentum and ten in a row all ended as clicks (74 to 172 ms, no moves, none cancelled)
  - **Checked on the S25** (Android 17), 2026-11-22 20:35, `wheel-scroll.mjs --pad scroll --app` (DevTools' wheel events in a visible Edge, the door on Wi-Fi): on the test pad a notch 188 of 191 phone px, three notches 564 of 574, a fast spin 2724 of 2871, touchpad swipes 608 of 629 and back 611, sideways 621 of 629, three swipes in a row 1798 of 1887, no fling after a lift; ten 100 ms clicks all clicks (held 9 to 234 ms by the time they landed); in Settings three notches 598 of 565, quick notches 567 of 565, touchpad 623 of 619.   - Not tried before that: the S25 and other phones on a newer Android (there a gesture is sampled at the screen's rate, so the old swipe's many moves would have scrolled in part; not measured); a real wheel or touchpad through the operating system (the wheel events came from DevTools and from the page itself, at a touchpad's and a fast spin's pace); the desktop app's window with a real phone (`phone-window-test.mjs` checks what the window sends, to a stand-in phone); a list's end, where the finger goes on as a finger would (pull to refresh)
- Ctrl+V types the computer's clipboard. Ctrl+A, C, X and Z go to the field. Escape is Back
- With no field focused, the arrows and Enter move the phone's focus (Android 13)

Limits, stated in the card and the window:

- One finger. Pinch and other multi-finger gestures are not sent yet
- From Android 16, injected touches are dropped on views an app marks sensitive (`filterTouchesWhenObscured`), which includes some banking apps
- Android 17's Advanced Protection turns off every accessibility service that is not an accessibility tool, this one included
- Android 16 does not let a user grant accessibility during a call with an unknown number

### The first computer after the app starts

With unattended access, a computer that arrives while nothing is shared gets the slow view at once, and screen sharing starts by itself a moment later (about 100 ms on the S25). The slow view's first screenshot can come back after the session has moved to screen sharing. Until 2026-11-22 that late screenshot still made an encoder and sent the computer its picture description, *slow view*, and its frames: when that description went out after screen sharing's own (2 ms after it, on the S25 at 09:55 that day, right after an update), the page showed the slow view for good, and *Full speed* did nothing, as sharing was already on. Now each source gets a feed of its own from the session (`PhoneStream.Feed`), and a source the session has left goes nowhere. Checked on the S25, the app's main process ended (as Android ends an app in the background) and started again before each run: with the old build, in six runs out of six, the session moved to screen sharing first, and the slow view's late description still reached the page (0 to 41 ms before screen sharing's; whichever goes last wins); with the fix, the same order on the phone in six runs out of six, and the page got screen sharing's description alone. The slow view alone (unattended access off) still comes, as before.

### When the app is stopped

- Swiped away in Recent apps (One UI, and Android itself): nothing stops. Android keeps every process of an app that has a foreground service when its task goes. On the S25, taking the app's four Recent apps cards away left all four processes, the door, the tunnel and control as they were
- Force-stopped (Force stop in the app's info; this was thought to be what a Xiaomi phone's Clear all does, but on the Redmi Note 7 it is a kill, see Battery and Autostart below): every process ends, screen sharing with them, and Android takes the app's accessibility service off its enabled list, without a word to the app. On the S25 the list went from ours to `null`, and accessibility off. Opening the app brings Remote desktop back (the door, the tunnel and the daemon were up 12 to 15 s later), but not control: only the person at the phone can turn that on again
- Until 2026-11-21 a computer then found nothing: the stream listened only while control or screen sharing held it, so the door answered "Remote desktop is not running on the phone" and the phone was never asked (the S25, red, and a Redmi Note 7 the same way for the person testing). - And when control was on and Android turned it off, *Turn control back on for Remote desktop*, which opens Android's accessibility settings. On a Xiaomi phone it also says that Clear all in Recent apps closes the app and that, with Autostart on, the app starts again by itself. ## Awake while a computer has it

A computer that opens the phone turns its screen on (`PhoneWakeActivity`: `setTurnScreenOn` and `setShowWhenLocked`, allowed from the background because the accessibility service is bound) and keeps it on with a one-pixel window of the service's own (`FLAG_KEEP_SCREEN_ON`). When the computer goes, the window goes, and the phone sleeps by its own timeout. The window can say `"wake":false` in its hello to leave the phone as it is.

The window sends one byte every 50 ms while it is in front. The phone drops it; it exists to keep the phone's Wi-Fi out of power save, which on the S24 took a round trip from 138 ms to 35-47 ms.

A click or a key on a phone that has gone to sleep while a computer has it (its power key pressed, or its own timeout) wakes it, and does nothing more: the person sees what is there before anything is touched (`PhoneInput`).

## A locked phone

Android draws the lock screen's PIN pad, password box and pattern in a secure window. Screen sharing shows it black, and so do the control service's screenshots (the slow view). On a Galaxy S25 Ultra, Android 17, even adb's own `screencap` is black there. The lock screen before it (the clock, *Swipe to unlock*) shows as it is. scrcpy has the same limit; what works there is typing the PIN blind, because adb can inject keys. An app cannot inject keys into another app's window, so typing did nothing here, and the person at the computer saw a black screen with nothing to type into (the user's report, 2026-11-22).

`PhoneLock` reads the pad through the control service, as a screen reader does, a few times a second while the phone is locked and a computer has it. While the phone is locked it reads every view and each view's id (`FLAG_INCLUDE_NOT_IMPORTANT_VIEWS` and `FLAG_REPORT_VIEW_IDS`, set in `PhoneControlService.seeAllViews` and taken off again once it unlocks): a Galaxy marks its "Enter PIN" line and its OK key as unimportant for accessibility, and the OK key (`key_enter_text`) and the pad's own lines are known by their ids, which Android leaves out unless asked. The phone sends `{"t":"lock","pad":"pin",..}`: each key's place, how many digits are in the field (never the digits; a password field gives its length as dots), and the pad's own words ("Enter PIN", "Wrong PIN", "Try again in 30 seconds"). The window draws them where the picture is black, and only there: a phone that does show its pad is not drawn over. Nothing drawn takes a click: a click goes through as a tap on the real key below.

The computer's number keys, Backspace and Enter press the pad's own keys (`ACTION_CLICK`, a screen reader's double tap). A digit typed on the lock screen without its pad brings the pad up first (a swipe up, as a person does) and goes in once it is there; typed while the phone sleeps, the screen comes on first. Only the lock screen's own window is touched (System UI's, in front): never while a call or the camera shows over it, and never its *Emergency call* button. A password or a pattern is drawn too (the box, or the pattern's nine dots), and typing a password goes the usual way, into the focused field.

**Checked**, S25, `test/phone-remote/sound-lock.mjs` through the door, 2026-11-22: with the PIN pad up (`wm dismiss-keyguard`, no tap) the page drew 11 keys over the black picture; two digits typed on the computer's keyboard reached the phone's PIN field (`n: 2`), and two Backspaces took them out. Nothing was ever submitted: the test never presses OK and never types a whole PIN. A digit typed on the lock screen brought the pad up and went in (`n: 1`). A click on the sleeping phone woke it (Dozing to Awake), and the lock screen stayed, without its pad. The same test on the previous build: no pad drawn, the digits never reached the field, and the click left the phone asleep. The desktop app's window draws the same pad from the same message (`phone-window-test.mjs`, a stand-in phone).

**The words and the OK key**, the same test later that day: with every view but no ids (the build of 14:56), the pad came with 11 keys, digits and Delete found by what they say, and with no OK key and no words (Android's `dumpsys accessibility` showed the service fetching with `fetchFlags=128`, unimportant views, and without 256, the ids). With the ids too (15:22): 12 keys with OK, and the words *Enter PIN* and *Your PIN contains at least 4 digits.*, all drawn (`fetchFlags=384` while locked).

**The wider view is put back when the computer leaves.** Only the lock watch put the usual view back, and only on seeing an unlock, so a computer that left while the phone was locked left `fetchFlags=384` on (seen on the S25 after the 15:36 test). Since 2026-11-22 the last lock watch to stop puts it back too (`PhoneStream.LOCK_WATCHES`). **Checked** on the S25 at 16:53 that day (scratchpad `lockflags-check.mjs`: the phone locked by its sleep key and woken to its lock screen, nothing typed or touched, a client of its own with `wake:false`): `fetchFlags=384` while the computer had the locked phone, `0` once it said goodbye with the phone still locked. The old code's red is the 15:36 run's `384` after its computer left.

**Not checked:** an unlock itself (it needs the owner's PIN: try it from a computer); a password or a pattern lock (the S25 has a PIN, the Redmi Note 7 no secure lock at all); other makers' lock screens (the keys are found by what they say, a single digit, and the Delete and OK keys by AOSP's own ids, which a Galaxy keeps).

## Quality

| | Longest side | Frames | Bitrate ceiling |
| --- | --- | --- | --- |
| Low (fast) | 1280 px | 60 | 4 Mb/s |
| Medium | 1920 px | 60 | 12 Mb/s |
| High | the screen's own | 60 | 30 Mb/s |

All three keep 60 frames a second, because a phone's screen moves with the finger. The bitrate starts from the picture's size and goes down as soon as frames arrive late (`LinuxStreamRate`, from the times in the acknowledgements, on the local network) and back up while they keep up. The window chooses, and remembers the choice; one that says nothing gets Medium. The phone has no quality setting of its own: the person at the computer is the one who sees the picture and how the link holds up. A smaller phone screen (the S25 Ultra's default is 720x1560) is never drawn larger.

## Picture size

A dropdown after Low, Medium and High, in the page (the door's, the tunnel's and the page from anywhere) and in the desktop app's window: *Full size*, *Three quarters*, *Half size*, *A third*. Each is that part of the quality's own picture, in width and in height: Half size on Medium sends 360x780 from the S25 Ultra's 720x1560, and on Low, half of Low's 590x1280 (294x640). ## Sound

A dropdown after Picture size, in the page and in the desktop app's window: *Sound on phone* (the default), *Sound in browser* (*Sound on computer* in the app), *Sound on both*, *Sound off*. Two switches on the wire (`{"t":"audio","on":..,"phone":..}`, and in the hello): `on`, the phone's sound sent here; `phone`, still played on the phone. *Sound on phone* and *Sound off* read nothing and send nothing, so the whole link and the phone's processor stay the picture's. *Sound in browser* and *Sound off* keep the phone itself quiet.

- **What is heard** is Android's playback capture (Android 10 on), through the projection screen sharing already holds, so the sound comes with full speed and not with the slow view (the window says so). What apps play as media, games and unknown: calls, ringtones, alarms and notification sounds stay on the phone, and so does an app that does not let itself be captured. Android asks for the microphone permission for it (*record audio*), which the Settings page explains before Android asks; the microphone is never opened. A computer that asks without the permission is told so, and the phone asks: a notification, and the question itself over the phone's screen when control is on.
- **Read as Linux's sound is read** (`LinuxStreamAudio`, with the capture as its tap): Opus at the picture's quality (96 kb/s stereo at Medium, 32 kb/s mono at Low), lossless PCM at High, silence held back after half a second. The page plays it with the same player as Linux's page (`sound.js`; `sound.ts` in the app).
- **The phone kept quiet** is its media volume muted (`ADJUST_MUTE`), which the capture does not hear: the capture's output is at unity gain whatever the volume (checked: muted on the phone, the page still got the tone at full level, on the S25 and the Redmi Note 7). Muted only while a session asks, and unmuted after, unless someone at the phone turned it up first; a mark in the app's files has the next start unmute a phone a killed process left quiet.
- **A browser starts sound only after a click or a key** in the page. Chosen from the list, it starts at once; chosen before and the page reloaded, it starts at the first click on the phone's picture, and the status line says *click the screen to hear the phone* until then.

**What it costs**, S25, one session through the door, the phone playing a tone throughout, the choice switched every 20 s, three times each (`/proc/<pid>/stat`): the app's process 1.3% of one core with sound on the phone, 14.0% with sound in the browser; Android's audio server 13.3% and 14.7% (the tone's own playback is most of that). And about 96 kb/s on the link at Medium. A latency comparison was run too (4 runs of 30 taps, interleaved), but the Wi-Fi cut the picture's bitrate to its floor in runs with and without sound alike that afternoon, so it shows nothing either way and is not quoted.

**Checked** with `sound-lock.mjs`, 2026-11-22: S25 (Android 17) and Redmi Note 7 (Android 10, MIUI 12.5) through the door, every choice: what is sent (nothing on the phone and off, Opus 96 kb/s otherwise), what the page plays (70-80 runs of the tone loud), whether the phone is muted, the permission's question and notification, the volume as it was after. The desktop app's window with a stand-in phone (`phone-window-test.mjs`). Through the Cloudflare tunnel too: S25, 2026-11-22 20:40, `sound-lock.mjs --only sound` with the tunnel's address, 20 of 20 (Opus 96 kb/s, 99 sound messages, 76 loud runs, the phone muted and still heard, the volume as it was). **Not checked:** sound from anywhere, or in the desktop app's window with a real phone; how far the sound lags its picture.

## Leaving

Closing the page's tab, or going elsewhere in it, while the phone is on screen is asked first (the browser's own *Leave site?*, as Linux's page asks). Gone, the page tells the phone (`{"t":"bye"}`) before its link closes, and the phone ends that browser's session there and then: its sound stops, the phone's own sound comes back, the screen is let sleep, and Remote desktop stays on for the next computer. On Wi-Fi the link's own close ended a session within about 1.4 s before; through a relay that can take far longer. Checked: S25 and Redmi Note 7, the question came, and the phone ended the session 186 to 265 ms after the close (by the phone's clock). The desktop app's window says goodbye too when it closes, without a question.

A computer that vanishes without a word (a tab killed, a lid shut, the network gone) holds the phone 90 s at most: the stream's socket reads with a 90 s timeout once the hello is in (`PhoneStream.SILENT_MS`), and a page that is up sends something at least every 2 s, hidden tab or not. **Checked** with `test/phone-remote/vanish-check.mjs`, S25, 2026-11-22, the phone locked: a client of the script's own signed in, opened the screen, asked for the sound with the phone quiet, then sent nothing. The phone ended its session 90 s later (15:37:40 to 15:39:10 by the phone's log) and its own sound came back. Not run on an older build, so there is no red run for it.

## The wire

`LinuxStream`'s, after a WebSocket upgrade on `/phone` (see the comment at the top of `PhoneStream.java`), so the window decodes with the same code and the bitrate rule works unchanged. Coordinates are the phone's screen pixels (`dw`×`dh` in the video message). Additions: `text`, `key`, `clip`, `share`, `quality`, `size`, `picture`, `audio` and `bye` from the computer; `phone` (control, screen on, locked), `audio` (the sound's state), `sound` with `0x03` runs (as Linux's) and `lock` (the hidden PIN pad) from the phone. One binary addition from the computer, `0x13`: the wheel and a touchpad, with x, y and how far the page there scrolls in the phone's pixels, one message for each wheel event. The pointer message's bits 3-6 (RFB's wheel) count notches only, a press and a release each, and a touchpad's small steps would be dozens of messages a notch; the phone still takes them, as Android's own notch of 64 dp. The test pad (`testpad`; `"busy":true` draws the whole screen anew at each touch) and the test tone (`testtone`, a tone the phone plays as media) answer only on a build a test has given `files/phone-remote/testpad`, which needs `run-as`, so never on the Play build.

The tunnel: `desktop/1` has a `phone` op beside `stream`; the daemon puts it through to `@<package>.phone-stream` (`--phone-socket`, which RemoteHost passes where the APK declares Remote desktop). With only Remote desktop on, the tunnel runs for it alone: sshd does not start, and SSH and the Linux desktop are refused as `linux-off`. A `phone-rtc` op carries the WebRTC signalling for the page from anywhere (`RtcSignal` frames: offer, answer, candidates, `up`); its data channel, named `phone`, then carries what the `phone` op's stream does, byte for byte.

Who is watching is said by whoever let the viewer in, never by the viewer: the door adds `x-dex-via: wifi` or `tunnel` to the upgrade it passes on, the daemon `x-dex-via: remote` and `x-dex-peer: <the computer's name>`, and both drop any `x-dex-*` the viewer sent itself. PhoneStream names the session from those, for its log and the Settings page ("a browser, through the Cloudflare tunnel"; "Browser on Win32, through remote access").

## Who gets in, and what to

- **A computer** paired with the code gets whatever the phone's switches offer: the phone's screen, and with Linux's remote access on, SSH and Linux's desktop
- **A browser** paired with the code through the page from anywhere is recorded as `os: browser`, `scope: phone` in `peers.json`. Its key lives in a web page's storage, so it gets the phone's screen and nothing of Linux's: its key never goes into Linux's `authorized_keys`, and the daemon refuses it SSH and the Linux desktop's ops and tells it of no Linux features (checked on the S25: its status offers `phone` alone, a computer's `desktop, desktop-stream, phone`). A web page's storage is shared by every page of its origin, so the page should live on an origin of its own (not a shared `github.io` origin), and *Forget this phone* on the page takes its key away
- **A browser through the door** (same Wi-Fi or the Cloudflare tunnel) has a token from the six-digit code. *Sign out every browser* on the phone, a browser's own *Forget*, and the door stopping end that browser's phone stream at once, not only new ones (the token is checked when a stream opens, and a stream outlives that check). Through the tunnel the door gives the phone's page, screen and files only (`/pfs/`), never Linux's page, files or desktop, whatever Linux's own switch says; loopback by any other name gets nothing
- The six-digit code's wrong-try budget (ten tries, then the code is used up until the phone shows a new one) is shared by everybody on purpose: per address only, a crowd of addresses would get unlimited tries. Each address also waits after five wrong codes (through the tunnel, the address Cloudflare saw). Codes work only while the phone shows one, so a stranger with the tunnel's address can at most use up a code while the owner is pairing
- **A browser with an email's sign-in link** (*Email me when an address changes*, `address-email.md`) gets what a code gives, with nobody at the phone: once, at the address the link was made for, for a day, and only the newest email's links. *Sign out every browser* ends the links with the browsers. The secret travels after the link's `#` and in the body of one POST over TLS, never in a request's address

## Files

*Files* on the phone page's bar opens the phone's own storage in the browser: the file manager Linux's page has (`linux-browser.md`, "Files"), with the phone's places down the side (the phone's storage at `/`, then Downloads, Camera, Pictures, Documents, Music and Movies where those folders are). Files or whole folders dropped onto it are copied into the folder open, and Upload does the same from the computer's own picker. A file dropped on the phone's screen, with Files closed, goes into Downloads, as scrcpy's drag and drop does. One file comes back as the browser's own download, several or a folder as one ZIP made on the way; Quick look shows photos, videos, songs, PDFs and text; Chrome and Edge can also save into a folder of the computer's. *Screen* goes back to the phone.

**The same door, the same token.** `/pfs/` on the door (`LinuxBrowserServer`), beside `/phone`, served by `LinuxFiles` of the phone's kind (`Kind.PHONE`) over the phone's shared storage (`/storage/emulated/0`), which `LinuxService` gives the door (`Host.phoneFiles`). A request comes in by the browser's token in `Authorization`, or, for what a browser fetches by itself (a download, a video's source), by a ticket of that browser's, as on Linux's page. Every change comes only from the page's own origin, and never by GET. The Cloudflare tunnel carries it too, since the tunnel is Remote desktop's; Linux's `/fs/` stays off the tunnel. While Remote desktop is off every request is refused (`{"error":"off"}`), a ticket's too. The page's route, words and places are `phone-files.js`; the rest is Linux's own `files.js`, `transfer.js` and `peek.js` (`createFiles(app, PHONE)`), so the two pages' Files stay one piece of code.

**What ends a transfer.** Each transfer is held with the token it came in by. A sign-out on the phone and the door stopping end every one at once, a browser's own *Forget* its own, and Remote desktop switching off ends them all within a second, however it was switched off (the door looks every half second while one runs). Linux's switch going off leaves the phone's transfers alone. A transfer that moves nothing for 90 s ends, as on Linux's page.

**Paths, and what stays as it is.** The page names paths from the storage's top (`/Download/photo.jpg`). The server follows each name on the way: `..` stops at the top, an absolute symbolic link starts again there, and a link leading off the storage leads nowhere (the shared storage itself takes no links; this is for whatever an app left). The storage ignores the case of names, and so do the guards. The storage's top, Android's own folders there (Android, DCIM, Download, Pictures, Movies, Music, Documents and the rest) and the camera's `DCIM/Camera` cannot be renamed, moved or deleted from a browser; what is inside them can. Apps' folders under `Android/` are read only: looked at and downloaded, never written. A file is sent into a hidden part file beside where it goes and renamed into place once whole, so a cut never leaves half a file in a folder, and the next try carries on from what arrived. A big file goes in pieces of 32 MB, a `PUT` each (Linux's page sends the rest in one): through the Cloudflare tunnel a request's body may be no more than 100 MB on Cloudflare's free plan, and the door takes a file piece by piece as it takes a resume.

**The same file again.** Replace, chosen when a name is taken, sends and writes every file of that drop (`force`): the same size and time is only a quick check, and two different files can share both. Until 2026-11-21 Replace kept the file there, without a word, whenever the two matched (found by an audit with two 12 MiB files; Linux's page in Edge did the same, red; the S25's page now writes the new bytes, checked on its own disk). Without Replace chosen (a retry after a cut, a drop where nothing clashed), a file already there with the same size and time is left as it is, so a retry never makes copies. Before a big file (8 MB and more) goes, the page asks the phone (`part`, with `fresh`): a file already there the same is then not sent at all (the transfers' panel says *1 already there*), and what the phone would refuse at once (no room, apps' folders, a folder that went) is said before a byte goes. Asked after the body started, the answer is lost: the phone answers without taking a body it will not keep, and a browser, which reads no answer while it is still sending, sees only the reset when the phone hangs up on the rest. Until 2026-11-21, Replace on a big file already there sent all of it again and again, and every try met the reset: Linux's page in Edge 157, against this computer's door, sent an identical 20 MB file four times in 15 s without finishing, and the page's rule gives up after eight tries (about two minutes) with "The phone stopped answering". The phone's page is the same code (`transfer.js`, `LinuxFiles`); on the S25 itself, Edge sending the same 3 MiB twice got "Failed to fetch" for the second. The phone also reads to its end a body that comes anyway, so that its answer arrives.

**Pause, Cancel, Try again.** The page's transfers are Linux's (`transfer.js`), so the fixes of 2026-11-22 hold here (doc/linux-browser.md, "Sending"): Pause or Cancel pressed while the page asks the phone about a big file stops the transfer there, and nothing is sent after the button; *Try again* after one file of a drop failed sends every file of the drop that stopped; Cancel stops a drop still being made ready, and a Save into a folder still reading its folders; a file cancelled while it comes into a folder leaves nothing there, not an empty file. Checked in Edge against the launcher's own server (`test/linux-files-test.mjs`, red then green, DevTools holding the question until the button is pressed), and Cancel and Pause on the S25 itself (`test/phone-remote/files-cancel.mjs`, a 20 MiB film in `/Download/oadx-files-test`): with the build before the fix, Cancel sent the film anyway and the phone's copy changed, and Pause sent it while the panel said *Paused*; with the fix, nothing was sent after either, the phone's copy stayed as it was (checked on its own disk), and Resume asked again and sent it. The drop and Save-into-a-folder fixes were checked on this computer only.

**No Trash.** Android's own (MediaStore's) asks on the phone before anything goes in, which nobody at a computer can answer, so *Delete* asks in the page and deletes for good.

**The picture while Files are up.** The page tells the stream `{"t":"picture","on":false}`, as a hidden tab does: the session stays (the phone stays awake for it, and *Screen* brings the picture back at once, from a key frame), and no frame crosses the link while files do. Keys typed in Files never reach the phone.

**Permission.** With All files access (`MANAGE_EXTERNAL_STORAGE`) the app reads and writes the shared storage directly, as it does for Linux's shared folder. Remote desktop's card says whether a browser's Files has the phone's files; where it has not yet, *Allow access to all files* says what the permission is for and that switching it off later closes the app, then opens Android's own screen for it. The page says the same in plain words (the door's `noaccess`).

**Android 10** has no All files access. There the app declares the older storage permission (`READ_EXTERNAL_STORAGE` and `WRITE_EXTERNAL_STORAGE`, with `maxSdkVersion="29"`) and legacy storage (`requestLegacyExternalStorage`, which Android 10 honours and Android 11 ignores). The card's *Allow access to all files* then asks Android's own two-button storage question instead of opening a Settings screen, and the card counts the storage permission as access (`WebFiles.phoneFilesAllowed`). Until 2026-11-22 Android 10 got no Files at all, which the person testing on a Redmi Note 7 asked for. **Checked** on that Redmi Note 7 (Android 10, MIUI 12.5), 2026-11-22: Android's question, Allow, then the door's `/pfs/info` and a listing of the storage answered 200 and the card turned green; Android gave the permission `RESTRICTION_INSTALLER_EXEMPT` (an `adb install`), and `LEGACY_STORAGE` read allow. Not checked: an APK installed from a browser download or a store, where Android 10 may treat legacy storage differently. Android 9 and older get no Files (`WebFiles.phoneFilesOffered`).

**Granted is not usable on Android 10.** Android 10 can grant the storage permission and still keep the storage from the app (legacy storage refused). Until 2026-11-22 the card counted the permission alone, so it could say green while the door said `noaccess`. Now both go by `Environment.isExternalStorageLegacy()` too, and the card offers no link in that state, as asking again changes nothing. Shown red then green in `PhoneRemoteSettingsTest` (Robolectric, with Android 10's version set for the test). Not shown on a phone: on the Redmi Note 7, Android ignored `appops set --uid … LEGACY_STORAGE ignore`, so the refused state could not be made there.

**Google Play's build has no Files.** Its manifest takes `MANAGE_EXTERNAL_STORAGE` out (`linuxapp/src/release/AndroidManifest.xml`), so the door answers `unavailable`, the page shows no Files button, and the card says nothing of files. The release manifest takes Android 10's storage permission and legacy storage out too (above), so the Play build declares no storage permission at all. The way for that build would be a folder the person picks on the phone (the Storage Access Framework's `ACTION_OPEN_DOCUMENT_TREE`, kept with a persisted permission; Android 11 and newer refuse the storage's top and Download as a tree), served through `DocumentsContract` rather than `java.io.File`: a second backend for every operation `LinuxFiles` has (listing, ranges, part files and resume, ZIP, rename, move, delete), and a place on the card to pick and change the folder. Not built yet.

**The page from anywhere** (`openandroiddex-remote/web`) runs the same `phone.js` with no door behind it, so it has no Files: the button stays hidden and nothing of Files loads.

## The phone's helper: screen off, and the buttons Android keeps for a person

Two things an app may not do, which a process with the shell's authority may: power the phone's own panel down while the phone stays awake (scrcpy's screen off, to save the phone's battery while a computer uses it), and press what Android keeps for a person at the phone. The helper (`PhoneHelper.java`) does both for the app (`PhoneHelperLink.java`), and only those.

**Screen off.** No app API powers the panel down and leaves the phone running: a black window would black the picture too (screen sharing shows every window), and a window's brightness can only go to the lowest the phone allows. SurfaceControl's power mode does it (POWER_MODE_OFF, 0; NORMAL, 2), from the shell only, as scrcpy's server and our own `openandroiddex-wmd/Screen.java` do: the built-in panels' tokens from SurfaceControl (Android 10 to 13) or DisplayControl, loaded from services.jar (Android 14 on). Android still believes the screen is on, so the phone stays awake, screen sharing keeps sending pictures (its virtual display is composed as before; the panel's own composition stops, `numLayers=0` in SurfaceFlinger's dump), and the computer's taps keep landing. The page's *Screen off* button (and the desktop window's) asks for it; the browser keeps the choice, so a page that comes back darkens the phone again. The panel is lit again when the computer asks, when its session ends for any reason (the page closed, the computer gone quiet for 90 s, another computer taking the phone), when the app's process goes (the helper's connection ends with it, and the helper lights the panel), and on the helper's own `--quit`. Lighting it can fail (SurfaceControl's call throws). The app then still tells the computer the screen is off, and asks again at its next look (a session's change, or 5 s): only the helper's `on` counts as lit. A helper whose connection ended keeps the dark panel on its record until the panel is lit, tells a new connection that the panel is dark, and tries again at each look of its watch (every 300 ms). `--quit` and the helper's own end try up to five times first, because nothing tries after them. A person pressing the phone's power button while it is dark puts the phone to sleep (Android thought the screen was on); the helper sees the sleep within 300 ms and wakes the phone with KEYCODE_WAKEUP, so that one press brings the screen back, as a person expects, and the computer's wish is dropped until the computer asks again. The computer's own lock key says `forget` to the helper first, and that sleep is left alone.

**A screen someone else made dark.** Another tool can have the panel dark already when the computer asks: an Open Android DeX desktop's or scrcpy's screen off uses the same power mode, and Android still says the screen is on. Until 2026-11-23 the helper lit the panel at the session's end whatever had made it dark, so closing the window undid that tool's screen off (seen on the S25 while another session's DeX desktop had its screen off). Now the helper asks SurfaceFlinger first (`dumpsys SurfaceFlinger --displays`, the built-in panels' `powerMode`; Android 10 to 12 know no `--displays` and print everything, where the line under `+ DisplayDevice{… primary …}` says it; about 15 ms on the S25 and 40 ms on the Redmi Note 7). A panel found dark is left dark when the session ends: the window closed (the app asks `restore`, not `on`), the app's process gone, `--quit`. The window's own *Screen on* still asks for `on`, which lights it: the person asked for the screen. A panel a helper of this app made dark, and that is still dark because that helper died first, is not someone else's: the helper keeps a mark while the panel is dark because of it (`/data/local/tmp/<package>.panel-dark`, holding the boot's id, so a restart of the phone forgets it), and such a panel is lit at the end as before. This is the helper's protocol 2: an update keeps the old helper running, and a protocol-1 helper would answer `restore` with `error unknown` and light the panel on `on`, so the app tells it to go at the handshake (as for any older helper) and the new one starts, by itself on Android 11 and newer, from the computer's command on Android 10. When SurfaceFlinger's answer cannot be read, the helper does as before. Not handled: a tool that darkens the panel after the helper did (that darkening changes nothing SurfaceFlinger shows), whose screen off the session's end still lights.

**Input Android protects.** From Android 14 a view marked sensitive, or one that filters touches when obscured (permission questions, the installer, the screen-sharing consent, some Settings switches), is left out of the node tree for an accessibility service that is not an accessibility tool, and from Android 15 (a flag in View's `onFilterTouchEventForSecurity`) drops such a service's gestures. Our control is not a tool and must not claim to be (Play's policy). So while the helper is linked, the computer's finger, wheel and keys are real input events put in by the helper (InputManager's injectInputEvent, InputManagerGlobal from Android 14), as scrcpy's are: a finger is a touchscreen's down, moves and up (one way for the whole press, decided at its start; a finger left down when the link goes is lifted by the helper), the wheel is a mouse's ACTION_SCROLL (AXIS_VSCROLL is up, so a browser's dy goes negated, in units of the phone's scroll factor), keys are a keyboard's key events, and text is the key events Android's virtual keyboard map gives for it (what has none, an emoji, goes the accessibility way). Back, Home, Recents and the shade stay global actions. Without the helper nothing changes, and from Android 14 a press on a protected app's window (`PhoneInput#protectedAt`: Android's permission controller, its installer, SystemUI's own activities) tells the computer, which says in plain words that Android lets only someone at the phone press there, and how the helper changes that.

**Starting it.** A computer with adb runs, once after each restart of the phone, the command the page shows (*Screen off* while no helper runs, and the note's Copy button): `adb shell "CLASSPATH=<the app's base.apk> setsid nohup app_process / com.ccrstech.openandroiddex.launcher.PhoneHelper <package> <port> <key> >/dev/null 2>&1 </dev/null &"`. The APK's path changes with every update, so the page always shows the current one. `setsid nohup` keeps the helper when adb's shell ends: it runs as the shell with init as its parent until the phone restarts or `PhoneHelper --quit <package>` (from the shell). An update of the app keeps the running helper, which then still runs the old code: the handshake's three lines never change, so an app whose helper has a newer version tells the old one to go (`quit`), and the page shows the command for the new one.

**The link.** Android's SELinux keeps an app and the shell out of each other's local sockets in both directions: on the Redmi Note 7 (Android 10), `avc: denied { connectto } scontext=untrusted_app tcontext=shell` for the app's connection to an abstract socket of the shell's, and `scontext=shell tcontext=untrusted_app` the other way (adb's own forwards come from adbd, another domain). So the helper listens on a TCP port of the loopback address, chosen by the app once (42000 to 48999) and kept with a 256-bit key in the app's private files (`files/phone-remote/helper-key`); the command gives both to the helper. Every app can reach a loopback port, so each side proves it holds the key before anything else (HMAC-SHA256 over the other side's random challenge, a different word for each side so one proof cannot be sent back as the other). The key is visible on the helper's command line to the shell and root only (Android hides other users' processes from apps). The app's uid is also its Linux guest's, which can read the app's files: as for the stream itself, the app, its Linux and the computers it paired with are trusted alike, and nothing else on the phone gets in. While the helper runs, whoever holds the key can press anything on the phone, as a computer on the cable can; it ends with the phone's restart.

**Without a computer (Android 11 and newer).** The app starts the helper itself through the phone's own Wireless debugging, as Shizuku and LADB do (`PhoneHelperStart.java`, `AdbWire.java`, no library):

- **Once: pairing.** Settings, Remote desktop, *Set up Screen off*: Developer options on, Wireless debugging on, then *Pair device with pairing code*. The code goes into the app's notification (its reply box), because leaving Settings closes the pairing dialog. The app finds the pairing service over mDNS on the phone's own addresses (`_adb-tls-pairing._tcp`) and pairs its own adb key (RSA 2048, kept in `no_backup/phone-helper/adbkey`, never in a backup) as adb's computers do: TLS 1.3 with a certificate nobody checks; 64 bytes of the session's keying material (label `adb-label` with its NUL, Android's `SSLSockets.exportKeyingMaterial`) appended to the code as SPAKE2's password (BoringSSL's spake25519, the app as Alice, the names `adb pair client` and `adb pair server` with their NULs); AES-128-GCM under HKDF-SHA256 of SPAKE2's key for the two PeerInfos (the app's public key one way, the phone's `adb-<serial>-<random>` name the other). Android then lists the app under Paired devices (`LinuxOnDroid@<model>`).
- **Each start** (a computer connects, Screen off pressed, or right after pairing): Wireless debugging's connect service over mDNS (the name the pairing gave, else any on the phone's own addresses), adb's CNXN and STLS on 127.0.0.1, TLS 1.3 with the app's key, then one `shell:` stream running `pm grant <package> android.permission.WRITE_SECURE_SETTINGS; CLASSPATH=<apk> setsid nohup app_process / …PhoneHelper <package> --register &`. The shell then waits until the helper leads a session of its own (its `/proc/<pid>/stat`), and only then says `started` and ends: when adbd's plain `shell:` service (no shell protocol) ends, it takes everything still in the shell's process group with it, so a helper that has not yet run setsid never starts (see the check below). The wait ends at the first look in practice, and after 3 s at most.
- **No secret on that link.** adbd's certificate is a fresh key each time adbd starts, so nothing on the phone can vouch for the other end, and any app could listen on a loopback port and answer like adbd. So the helper makes its own port and key (`--register`) and hands them to the app through Android: `content call` to the app's `PhoneHelperDoor`, which the manifest guards with DUMP (the shell holds it, no app is given it) and which takes a key only when `Binder.getCallingUid()` is the shell's (2000) or root's. The trust manager takes the phone's own loopback address and nothing else.
- **Wireless debugging switched by the app.** With WRITE_SECURE_SETTINGS (granted by the helper's first start), the app switches Wireless debugging on when a start needs it and the phone is on Wi-Fi. On a Wi-Fi Android was never allowed on, Android puts the switch back within half a second and asks on the phone (*Allow wireless debugging on this network?*), which only someone at the phone can answer; a start nobody asked for is then not tried again on that network. Two minutes after the last computer leaves, or two minutes after a start no computer watches (Settings' *Try again*, or a computer that left while the start still ran), the app switches Wireless debugging off again, but only when the app switched it on (a mark in `no_backup`): a person's own Wireless debugging, and the computers on it, are left alone. The time is kept on disk (`switch-off-at`, the wall clock) and in an alarm Android keeps (`AlarmManager.setAndAllowWhileIdle`, RTC, received by `PhoneHelperStart$SwitchOffReceiver`), as well as on the app's main thread. Until 2026-11-23 it lived on the main thread alone: the app's process dying within the two minutes (Android's memory, an update, a crash) left Wireless debugging on until a later computer came and went, and so did a start no computer watched, and the phone's deep sleep (the main thread's clock stops there) put it off. A restart of the phone, or a force-stop (the desktop app's clean-up, or a person's), ends Android's alarms too, so the app looks again when it comes back: its restart receiver (`RemoteResumeReceiver`, at a restart, an update and the desktop app's clean-up) and Remote desktop's listener starting (`PhoneListenService`, which also covers a person's force-stop on Android 11 to 14, where opening the app again sends no BOOT_COMPLETED). It switches Wireless debugging off at once when the time has passed. While a computer watches, nothing is switched off, and the alarm stays set (every 10 minutes) for a process that dies mid-session; that look and the computer's leaving change the kept time under one lock, so the ten minutes never overwrite the two. A switch-off that does not take (the permission gone, or the switch still reading on afterwards) keeps the mark and tries again ten minutes later: the helper's next start grants WRITE_SECURE_SETTINGS again. An inexact alarm may come some minutes late, and in Doze at most every 9 minutes: Wireless debugging then goes off a little later than two minutes, but it does go off. Checked on the Galaxy S25 Ultra (Android 17), 2026-11-23, on a USB cable so that the test's own adb link did not ride the switch, with Wireless debugging off to begin with and the desktop app's window as the computer (`desk-wd.mjs`): the window's arrival made the app switch Wireless debugging on and start its helper every time. With the app's process left alone, it went off 123 s after the window closed (the code before this, 122 s). After `am stop-app` (every process and service of the app ended, its alarms kept, as when Android ends an app): the code before this left Wireless debugging on for the 6 minutes watched and set no alarm; this code's alarm (RTC, Android's window +1 min 30 s) started the app's receiver at 14:41:00, the window's end, and Wireless debugging went off then, 235 s after the window closed. After `am force-stop` (alarms ended too): on through 2.5 minutes stopped, off 23 ms after the app's process started when it was opened again. An update over the old code's left-over mark: off 2 minutes after the update. `am crash` does nothing to a build that is not debuggable on Android 17, so it proves nothing there.
- **The helper lives as long as adbd.** With USB debugging on, adbd runs anyway. With Wireless debugging alone, its switch going off (or the phone leaving the Wi-Fi) stops adbd, and init takes the helper with adbd's process group; the next computer starts it again.
- **Without any of it** (no Developer options, no Wireless debugging, no pairing, or Android 10): Remote desktop is as it was. The Settings card and the computer's note say what Screen off would need, and a computer's adb command still starts the helper.

The video was made on the Redmi Note 7 with a debug build that had cloudflared taken out, so it shows what the Play build shows
- **Foreground service type**: `mediaProjection`, declared as "Media and content projection, streaming", with the same video. The service starts only after consent and enters the foreground before taking the projection (Android 10 and 14 rules)

The sound goes only to the user's own computers, end to end encrypted, so it is not "collected" in Data safety's sense; the privacy policy says the app can send what other apps play, and only when the person at the computer chooses it. `RECORD_AUDIO` alone makes Play require a microphone, which took 6 devices off the supported list: the manifest has `android.hardware.microphone` with `required="false"`, and 0.3.40 supports every device 0.3.37 did

## Measured

Galaxy S25 Ultra, Android 17, 720x1560 screen, on the same home Wi-Fi as a Windows PC, 2026-11-21 evening, Medium. **Click to picture** is measured in the viewer itself (`test/phone-remote/page-latency.mjs`): a real mouse press on the page's canvas over DevTools, at the test pad's square (a full-screen window of the control service's own that turns a square white or black at each touch down). t0 is when the page got the pointerdown, which is when it sends the touch; t1 is the first frame the page drew (its `drawImage`, in the page's own clock) in which the square changed. So the whole loop is in it, decoding and drawing included; not in it are the compositor showing the canvas (up to one display frame more) and the mouse reaching the browser. One tap at a time: the next goes only after this one's change was drawn, and a change no tap explains is counted (none were).

| Route (30 taps each) | Median | Best | p90 | Worst |
| --- | --- | --- | --- | --- |
| Browser, the door on the same Wi-Fi | 47 ms | 33 ms | 118 ms | 177 ms |
| Desktop app's Phone screen window (iroh, direct on the same Wi-Fi) | 73 ms | 40 ms | 187 ms | 1254 ms |
| Page from anywhere, direct (WebRTC, both ends on the same Wi-Fi) | 77 ms | 42 ms | 127 ms | 167 ms |
| Browser, Cloudflare tunnel (both ends on the same Wi-Fi) | 91 ms | 51 ms | 153 ms | 226 ms |
| Page from anywhere, through n0's relay (WebRTC taken away) | 154 ms | 77 ms | 373 ms | 1124 ms |

- No tap was lost in any run. A later Cloudflare run of 20 clicks gave 126 ms median (p90 314): the routes through a service vary from run to run, and five runs on one evening on one network are not a ranking of providers
- "From anywhere" in the table means the route, not the distance: phone and PC were on the same Wi-Fi for those runs
- The WebRTC route is slower than the door on the same Wi-Fi (77 against 47 ms), and why is not known yet (its SCTP, the data channel's chunking, or the page's own copying are the suspects)
- **Withdrawn:** numbers from before this harness (tunnel 62 ms, wireless adb 79 ms, the door 40 ms, Cloudflare 57 ms, the relay 449 ms) came from a client that sent taps on a timer and timed them to the encoded frame's arrival. It could credit one change to a later tap, and it never saw a picture drawn. Wireless debugging is not a route anyone uses for this and was not measured again
- The desktop app's window ran for the first time on 2026-11-21 (a test identity, its own APPDATA and home): paired with a code, opened the phone at 47-53 frames a second, 35-51 ms round trips

**With the phone on mobile data** (its Wi-Fi off for nine minutes, the PC on the home Wi-Fi), 20 taps each, all timed:

Not tried yet: another network for the computer; a whole unlock with a PIN from the computer (the digits reaching the pad are checked, see "A locked phone"); typing into a real app; more than one finger; TeamViewer on the same phone, so no comparison is claimed here.

**Seen once, after an update:** on 2026-11-22 an `adb install -r` while the S25 was locked, dozing and off its charger left everything down. Android never delivered the update's broadcast to the app (no process started for eight minutes, even after the screen woke), and left the control service at *Binding*. Back only after the receiver's own resume action (`am broadcast … remote.RESUME`) and control switched off and on. Three later installs, one of them while dozing too, came back by themselves within seven seconds. Why that one did not is not known. For a phone that updates from Google Play overnight it would mean Remote desktop down until the app is opened.
